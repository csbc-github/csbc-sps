# 線掃描取點修正（2026-11-13）

此修改將 IP_control 已驗證的 `scan_order_contacts_v3` 移入 ThreeDScan 的原生 C# 線掃描路徑。使用者指定的 `ThreeDScan/` 是 WPF 專案；API 入口位於同層 `ThreeDScan.Api/`，兩者共用 `ThreeDScan.Infrastructure/LineScan/`。

## 量測與原始資料

- `Hank/Geometry.cs` 與 `Hank/SceneContacts.cs` 保留光束順序，避免近直立邊按 X 排序後折返斷段。
- 頂點採有界的雙面擬合交點；端點必須受斜面支持。有支持的直邊可以接桌面，較平的斜面不強制延長到底線；新版不加入舊版固定高度補償。
- `LineScanMeasureService` 使用 `LegPoints` 建立頭尾角點，並接受逐圈串流；恰好兩個有效截面已可量測。
- `LineScanMeasurementContext` 優先採用錄製時保存的校正、ROI、平均及 Encoder 比例，避免錄完後修改設定影響既有任務。
- 量測從原始 `line_raw.ply` 重播，保留桌面附近最低至 -4 mm（若原設定更低則照原設定）的背景支持點。公開 3D PLY 的高度裁切與保存設定不變；沒有重新寫入或覆蓋公開點雲。
- 缺少原始資料或凍結設定時會回報錯誤，不從已裁掉桌面的 3D 點雲猜測接點。完成檔優先依 `line_raw.capture.json` 的 `output_3d`，並相容 `line_3d.ply`／舊 `line_raw_3d.ply`。

## 點數與預覽

- 兩套平均器共同使用 10 mm 群集與 `1e-9 mm` 邊界容差，保留相同射線的時間順序。
- live 快取使用端點設定的平均圈數（預設 20），與單次 profile 平均採相同規則；兩個平均視窗互不干涉，原始錄製仍接收每圈資料。
- 中斷、時間或角度範圍變化、設備異常與平均設定改變會重設平均，並清除失效快取。
- WPF 直接使用 API 的 double X/Y 點繪圖及選點，移除半徑取整數及均勻角度重分格造成的碰撞覆寫。

## API 相容性與尺寸定義

既有 `/api/scan/profile`、`/api/scan/line/live`、`/api/scan/line/complete`、latest 與 task 回應路由及 DTO 不變。

`headFeatures`／`tailFeatures` 與翼寬使用同一組擬合後端點。既有 API 的 `width` 保留頭端兩腳的三維距離，`height` 保留頂點相對兩腳連線的高度；`leftWidth`／`rightWidth` 是截面翼寬，`leftLength`／`rightLength` 是頭尾沿程長度。這些定義在可見端點高於桌面時，與獨立桌面工具的 X 跨度／距桌面高度可能不同，不能直接比較同名數字。

模型內部保留原始尺寸、端點動作、RMS／P95 及頂點移動量；沒有將內部診斷欄位加入公開 DAS DTO。對掃描點的貼合誤差不等於已驗證實物尺寸的絕對誤差。

## Encoder 沒有位置變化

2026-11-13 的實際失敗錄製包含 4,244 圈、約 7.071 秒的設備時間，唯一一個 Encoder 通道的位置最小值與最大值都是 0。原始點與 Encoder sidecar 都已保存；沒有產生成功的 3D 重建。

`StreamingReconstruction.BuildAndSave` 在平均、ROI 與高度篩選之前，檢查選取範圍內指定 Encoder 通道的原始位置跨度。跨度為 0 時仍拒絕重建，保留原始資料；調整平均、半徑或每圈計數無法補出未收到的位移。

- 若有轉動連著 Encoder 的測輪，先用 `/api/scan/profile` 回傳的 `encoders[].position` 確認位置是否隨轉動變化，再檢查現場接線、設備 Encoder 輸出及通道選擇。
- 若只要取得靜止角鋼的 2D 截面，使用 `/api/scan/profile`；此端點回傳平均 X/Y 點，目前不回傳靜態角鋼尺寸。`line/start`／`line/complete` 是需要 Encoder 位移的 3D 錄製流程。
- `line_raw.capture.json` 的錄製完成旗標表示原始資料收尾完成，3D 是否成功需另看重建結果與任務狀態。

修正 `SickCSharpLineScanner` 將裝置層完成錯誤轉為既有的 Domain `ScanTaskException`，並讓背景完成流程處理此例外及 `ArgumentException`。完成失敗會保存 `Failed`、`SCAN_LINE_002` 與原始原因，釋放任務的裝置占用，更新 latest 並嘗試回呼，避免任務留在 `Processing`。回呼網址無服務接聽造成的連線錯誤，需要另外處理；失敗狀態會先保存。

## JSON 切換實際／模擬 Encoder

模式只由載入設定中的 `LineScan:EncoderSimulation:Enabled` 決定，不額外檢查 Debug／Release 或執行環境。`appsettings.json` 預設 `false`，`appsettings.Development.json` 預設 `true`；ASP.NET 原有的設定檔載入與覆寫規則照常運作。Visual Studio／`dotnet run` 既有的 Development 啟動設定會載入 Development.json。改完設定請重新啟動 API。

```json
"LineScan": {
  "EncoderSimulation": {
    "Enabled": true,
    "ForwardSpeedMmPerSec": 100
  }
}
```

- `true`：掃描點仍取自實際光達；錄製開始時將 Encoder 位移改為固定正向速度，預設 100 mm/s，可調整 `ForwardSpeedMmPerSec`。這個速度是測試設定，沿程長度由速度與設備掃描時間決定。
- `false`：完全使用設備實際 Encoder；缺少通道或沒有位移仍會回報原本的錯誤。
- 使用真實 Encoder 時，將實際載入的 JSON 開關設為 `false`。編譯成 Release 本身不會改變這個 JSON 開關。

模擬按設備微秒時間累計計數，保留掃描點、時間與掃描計數器；相同封包不增加行程，沒有新掃描也不增加行程。`Direction=-1` 時補償計數方向，重建的 Y 仍往正向前進。模擬允許補入尚未接線的指定 Encoder 通道，其他通道保留。profile／架設預覽維持實際點資料與設備 Encoder 回讀，模擬只套用在 start／complete 錄製。

同時修正首次封包重複被誤認為 Encoder 重設的情況；重複封包仍交給 Recorder 檢查真實位置衝突。Encoder 去除重複後，平均區塊依設備 counter 連續性判斷，原始 Frame ID 跳號不會打斷平均；實際缺圈與空影格仍會切斷區塊，原始 Frame ID 保留供追溯。

每次錄製凍結模擬速度與 Encoder 比例。raw PLY 與重建 PLY 標記 `encoder_source synthetic`，Encoder sidecar 標記 `simulation: true`，capture 標記 `synthetic: true` 並保存 `encoder_simulation` 設定，重建報告也會標記 simulation。原始實際模式保留 recorded 標記。

## 驗證

在解法根目錄執行：

```powershell
dotnet build ThreeDScan.slnx -c Debug -p:Platform=x64
dotnet run --project tests/ThreeDScan.LineScan.Regression -c Release -p:Platform=x64
```

回歸工具包含固定場景與鏡像、Python 封包參考、浮點邊界、真正 Recorder／Encoder／凍結設定串流、實際量測與 DTO mapping，以及隔離的 Controller HTTP 測試。其 HTTP 主機只在隨機 loopback 埠啟動，替換 Application 的外部 I/O 邊界，不執行正式 Program 的資料庫啟動工作、不停用正式驗證，也不連接掃描器或發送回呼。

無位移回歸使用真實 `EncoderScanSession`，並離線驗證 Host → Scanner adapter → Domain 例外 → 實際背景佇列與 Application 的完成失敗流程；同時驗證回呼傳送失敗後，已保存的失敗原因與 latest／task 查詢仍正確。

另以實際編譯的 WPF 控制項驗證原始 X/Y、全部點數、凍結、繪圖及選點。實體掃描器與產線資料庫仍需在現場驗證。
